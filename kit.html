Docs · Using the kit

Put a device in your own page.

Portrayal compiles each device into ordinary files: an SVG per face, and JSON indexes beside them. Everything below runs here, live, and the code beside each result is the file that just ran it. This page documents @portrayal/kit 0.10.0.

Start here

A compiled device is one SVG per face (<device>.<config>.<view>.svg) plus devices.json, components.json and a <device>.configs.json and a <device>.source.json per device. The kit, @portrayal/kit, is plain ES modules with no build step; three.js is needed only for 3D. A face that several configurations draw identically is written once, so find a configuration's face with faceFile(index, config, view) from @portrayal/kit/dist rather than building its name; each device's default configuration is also at <device>.<view>.svg. The recipes below use the UfiSpace S9600-72XC.

Beside every face, under the same name, is <device>.<config>.<view>.elements.json: the face's elements as data, each with its path, class, part reference, box and connection points, so you can read a face's tree without parsing or laying out the SVG. It is read from the SVG beside it and adds nothing; its format is in Portrayal's format-stability.md. It comes with a build of library/dist/ (see Getting the files); portrayal.dev doesn't serve it.

The drawing is the API

No kit at all: fetch a face, insert it, and address its parts by data-path. A lamp is lit by a state class the drawing already styles; a click tells you which part it hit.

Color it from your data

A port is an element like any other, so your monitoring can paint it. Here the numbers are a table in the file; in a dashboard they are whatever your telemetry returns.

Read the device from the drawing

Each device publishes its source manifest once, as <device>.source.json: the device, its chassis in millimeters, its configurations. Every face names that file by its SHA-256 in <metadata>, so a drawing can be checked against the source it was drawn from. And devices.json lists everything in the library.

Seat an optic or a cable end

A cage is empty until you say what's in it. Name the part for the cage, and for an optic its two LC bores; the kit draws each part's own artwork into the face and refuses anything the cage doesn't accept.

In 3D

The same files, as a model you can turn over. The viewer takes the same paths and lamp states as the drawing (setStates; a state on a switched outlet reaches the lamp bound to it, as it does in 2D), the same text on parts (setFields), and exports GLB and USDZ (download). createViewer(el, {ears: true}) or setEars(true) adds the generic rack ears described below, and a GLB taken then carries them. It needs three.js; the page's import map says where that lives.

Rack ears

A published face has no rack ears: a device is drawn between its ear folds. @portrayal/kit/ears2d draws the generic L-bracket over the face you already hold, so a page can offer the ears as a choice: off by default in a device view, on in a rack. earPlan(configs, frontWidth) is the plan the 3D viewer builds from, and it is null where the device gets none: a front as wide as the rack (482.6 mm), whose ears are built into the face and drawn already, such as a blanking panel; a device that is not rack-mounted; or ears stated behind. The ear is silver (#c8cacc) unless the device states chassis.ears.color. drawEars(svg, plan, view) grows the viewBox to hold them and clearEars puts it back. The overlay is a picture, not a part: it has no data-path and takes no clicks, and an export of the live drawing carries it.

An outlet and its lamp

A switched PDU's outlet declares the states on and off, and the lamp that shows them is a part beside it, bound to the outlet with for:. Set a state on the outlet's path and it is shown on its lamp. @portrayal/kit/states has the one rule every place that applies a state uses: boundLamps(svg) maps each outlet's path to its lamps, and expandStates(map, bindings) turns a map keyed by outlets into one that reaches their lamps too (a lamp stated in the map itself keeps its own). A marks document, the Explorer's state chips and viewer.setStates all apply it, so 2D and 3D agree.

off can be lit: offIsSet(el, lamps) says whether an off chip sets state-off (an outlet, so its lamp shows the color its device declares for off, or a power outlet with no lamp, which is dimmed) or clears the element, as it does on a plain lamp. The module also reads a lamp's vocabulary (statesOfEl) and whether a state paints anything (paints).

Annotate and export

Describe what to mark, not how to draw it: a document of selectors, colors, lamp states and labels. A state on a switched outlet lights the lamp bound to it as well. The same document previews on the page, exports as an SVG you can drop into Word (toSvg), or as a PNG or GIF (toPng, toGif), and fits in a share URL (encode).

The Explorer shell

If you want the whole explorer rather than parts of it, mount the shell. It styles the page it lands in, so it runs here in a frame of its own. The Explorer is the full example, with 3D.

A rack, by commands

The rack/ modules are the Rack Builder's rules without its page. They read no DOM and fetch nothing but the rack catalog (rack.json) and the cable types, so a rack is checked the same way in a browser, in node and by an agent. Each is imported on its own, as @portrayal/kit/rack/<module>.

createRackEditor({doc, chassisOf}) holds a rack document and takes every edit as a named command through apply: place, move, patch, remove, attach, detach, frame, rename, dcim, fit, field, the side.*, zerou.*, cable.* and bundle.* commands. A batch lands whole or is refused with the reason; each batch is one step for undo and redo, and on('change') hears every one. COMMANDS in rack/commands names each command's arguments as JSON Schema, which is what an agent reads. preview answers what a batch would do without doing it.

To read a rack back, describe(rack, ctx) is the whole rack as text (or one stretch of a long one, with {section, offset, limit}), and inspect(rack, id, ctx) is one device, cable, part beside the rack or bundle as data. selectCables, freeUs, fitsAt and catalog answer what a command needs to know first.

Beside the rack

A part that stands beside the rack and takes no rack unit, such as a vertical cable manager, is an entry of rack.zeroU, not an item: zerou.place {ref, at, ru} stands it at an upright (left or right on a two-post, left-front to right-rear on a four-post), and zerou.update and zerou.remove move and remove it. The gutter beside that upright then runs through it, so a routed length is measured through the duct. A finger bracket narrower than the opening can stand on one rail: side.place and side.set.

Routes and ring marks

resolveRoute gives the waypoints a cable follows; routePath(rack, cable, ctx) is that route in millimeters, each D-ring expanded to where the cable enters and leaves it, and it is what routedLength, fill and the capacity checks measure. Each ring is decided once, there. ringMarks(rack, cable, ctx) hands those decisions to a drawing, one per waypoint, so the drawing passes through each ring the way it was measured. A mark's sense is along the rack's axes (x right as seen from the front, y up); a drawing whose axis runs the other way turns it with orientMarks, and a path drawn from its other end with reverseMarks:

import {resolveRoute, ringMarks, orientMarks, reverseMarks} from '@portrayal/kit/rack/route';
import {routed2d} from '@portrayal/kit/rack/route-path';

const marks = ringMarks(rack, cable, ctx);        // parallel to resolveRoute(...).waypoints
const front = orientMarks(marks, {y: -1});        // an SVG front elevation: y runs down
const rear = orientMarks(marks, {x: -1, y: -1});  // the rear, seen mirrored
const back = reverseMarks(front);                 // the same path, drawn from end b
const d = routed2d(points, 4, front);             // an SVG path through each ring, straight

The ctx comes from the drawings: guidesOf(itemId), the rings, ducts and pass-throughs on a part, and portX(end), a port's x in millimeters from the rack's center line. The recipe above uses a plain one, which routes by the gutters alone.

Bundles

Cables that share part of their route can be combed into a bundle and held with hook-and-loop straps. bundle.create, bundle.add, bundle.peel, bundle.update and bundle.remove make and change them, each one undo step. Given the routing context ({ctx: {route}}), bundle.create works the trunk out from where its cables run together (deriveTrunk), refusing a fork, a loop or groups that share nothing, by name; a member's own route then follows the trunk (followTrunk).

bundleCheck is the size check: the bundle's diameter, sqrt(sum(d²) / 0.8), against the smaller of 63.5 mm and each pathway's opening. It warns and never refuses. Each cable's diameter comes from its type: loadCableTypes(dist) reads cable-types.json and returns diameterOf, bendOf (the installed minimum bend radius) and typeOf. straps places the straps along the trunk, kept off rings.

Given bendOf as well, the check also looks at the bend: at each corner of the trunk, and at each pathway that states a radius, against the largest bend radius among the members there, so one fiber makes a bundle as strict as fiber. A corner's room is worked out from its legs and marked estimated. A miss is a warning, never a refusal. A member with no radius is listed as unchecked in the check's notes, never passed. inspect gives a bundle's bend as {radius_mm, by, unchecked, points, violations}; it is null only without the routes. cornersOf and bendCheck are exported for a page that draws them.

For the exports, bundleExports(rack, ctx) in rack/export-data measures every bundle once: its members, length, strap count, size and bend. Pass it to the cable schedule as cableScheduleRows(rack, ends, items, routes, {bundles}), whose notes then carry a line per bundle (bundleNotes); its bundle column names each cable's bundle. strapBomRows(bundles) is the bill of materials' one hook-and-loop strap line, every bundle's straps summed, and strapBomNotes says which bundles' straps could not be counted.

Getting the files

Two things: the kit's modules, and the compiled files they read.

The kit is on npm as @portrayal/kit. three.js is a peer dependency, needed only for 3D:

npm install @portrayal/kit three@0.161

This page documents kit 0.10.0, which is not on npm yet: npm's latest is 0.2.0. The rack and bundle modules, and everything else added since 0.2.0, are in the unpublished version only, so npm install gets a kit without them, and the CDN map below returns 404s. Until 0.10.0 is published, use the files from a Portrayal checkout's kit/ folder, or this site's own vendored copy (vendor/*.js and vendor/rack/*.js), and point the import map at wherever you serve them.

With a bundler, import @portrayal/kit/viewer3d and the rest by name; the package's exports resolve them. Without one, the modules are plain ES modules with no build step, so an import map pointing at a CDN is enough. List each module you use, pinned to a version:

The 2D recipes don't need three.js at all.

The compiled files are built, not downloaded. Clone Portrayal and run ./build.sh, which writes every device into library/dist/. The files are static, so serve that folder beside your page and set DIST in each recipe to where it is.

The compiled files are not on npm yet. Publishing them through a registry, split per device, is roc-ops/Portrayal #526 and #528; this section will change when that lands.
